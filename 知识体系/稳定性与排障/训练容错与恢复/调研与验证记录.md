## 文档与版本差异

1. 在线文档仍给出 inprocess.Wrapper 和旧依赖要求，但 v0.7.0 发布说明明确 inprocess 已弃用。正文以发布说明为新接入路线，不据“文档仍存在”推荐旧 API。
2. v0.7.0 README 支持矩阵为 PyTorch ≥2.8.0；pyproject 的安装依赖范围更宽（torch ≥2.3.0）。正文区分安装元数据和发布验证矩阵，不宣称后者以内的所有组合均可用。
3. Python 元数据允许 ≥3.10，发布 wheel / CI 针对 3.12、3.14。在线汇总 release-notes 有旧的 3.10/3.11/3.12 描述，正文采用 GitHub v0.7.0 release 的具体矩阵。
4. 配置类心跳默认 None；在线 Heartbeat 指南描述 launcher 可设置有限默认值。正文不写统一默认分钟数，强调显式配置及检查安装版本。
5. 在线 straggler 示例出现 nvidia_resiliency_ext.attribution.straggler 与 nvidia_resiliency_ext.straggler 两种 import。尚未核实全部打包兼容别名，正文不提供可直接运行的自编 API 示例，保留官方入口和语义解释。
6. 外部健康服务成功响应中的失败字段，release 说明和滚动指南存在 fail_count / failed_checks 差异。正文只写有效失败信号及 fail-open 边界，不硬编码有歧义的服务契约；部署时需对固定版本源码和服务联调。
7. 个别猜测的固定 tag 文档路径和 GitHub blob 网页未能抓取，不记为已读；可读取的 raw README / pyproject / config 及在线指南作为实际来源。

## 与当前工程的连接

用户现有工具基于 GPU 利用率 / 功率检测和历史堆栈，NVRx 进度监控可以补充，但还没有做并行对照。本文中的阶段划分、接入顺序和验证矩阵是设计建议，不是 NVIDIA 的强制推荐配置或用户亲历案例。

不推断用户已经掌握、接受某项实现，也没有将 GPU Hang 现有阈值复制成心跳超时。

## 后续验证问题

- 应用平台是否能替换 torchrun 入口为 ft_launcher，是否支持其进程树与 monitor 生命周期？
- worker 退出时平台会否结束整个容器 / 作业，与平台自动重试如何分工？
- 基础 resume 是否完整，成功 update 与 checkpoint 完成标记是否可靠？
- 正常初始化、编译、取数长尾、评估和 checkpoint 的耗时分布如何？
- 故障现场保留与恢复延迟如何取舍，上一轮堆栈和日志是否能跨 cycle 保留？
- 热备资源是否真实可用，副本是否跨节点故障域？
- 在隔离集群验证故障退出、无进展、半成品 checkpoint、健康资源替换后再讨论生产接入。

## 2026-10-16：按七部分重组 NVRx 报告

用户明确要求按功能、Quick Start、作业内容错与 Sections、异步 checkpoint、完整慢 rank 检测、失败归因、Shared Utilities 七部分重新梳理。已重写同名正式正文，保留原恢复流程图，兼容性、状态完整性和验证矩阵移至附录；不新增博客发布。

用户确认现有平台已支持多节点 / rank 日志检索与按重启分组。正文只给通用的“已有平台时按需补齐，不重复建设”建议，具体既有能力与接入决策保存在本私有记录。尚未决定是否部署本地聚合或 attrsvc。

本轮机制澄清：

- FT Sections 服务于超时检测，与 Straggler 计时 / 评分是不同 API。
- v0.7.0 Straggler 在区间边界启停 CUPTI CONCURRENT_KERNEL，不使用 CUDA Event / query；C++ 从活动记录读取 start / end 并统计。Detector.generate_report 开头显式同步 GPU，CUPTI flush 自身也是阻塞调用，但不隐式同步 GPU；不能将无显式设备同步等同于无开销。
- kernel 统计和 rank 级 GPU 分数不等于每步 forward / backward 的完整 GPU 阶段跨度；抽样周期按区间进入次数，报告周期按应用调用，local_* 细节不自动全部集中到 rank 0。
- 节点日志指南存在自动聚合说法；固定 tag LogManager 配置 handler、独立 log_aggregator 启动 NodeLogAggregator，故不认为只设置环境变量即完成聚合。
- 固定 tag TorchAsyncCheckpoint.async_save 在调用侧 preload_tensors 后执行 torch.cuda.synchronize，再提交后台写入；通用 AsyncRequest 的 preload_fn 路线需另行区分。正式正文已将“只在 report 同步”限定为 Straggler 稳态采集路径。

新增核验来源：v0.7.0 straggler.py、reporting.py、cupti.py、CUPTI 扩展六个 C++ / 头文件、log_manager.py、log_aggregator.py、TorchAsyncCheckpoint 与 straggler 包导出；在线 Straggler / Report API、Sections、异步 checkpoint、Logger / 聚合 API、Restart Agent 与 progressive attribution，以及 NVIDIA CUPTI Activity API。仅静态阅读，不执行库。GitHub API 文件树查询限流后改读官方 tag 源码包，读取到的指定扩展文件才记入核验；没有将失败的网页抓取当成已读。

验证：七章编号、内部锚点、本地链接和配图引用、代码围栏、四段 Python 结构语法及发布元数据检查通过。Python 无 PyYAML，未执行 YAML 解析；配置内容仅静态核对。未运行 NVRx、GPU / 多机 / checkpoint / K8s 恢复或性能测试；代码均标明为结构示意。
