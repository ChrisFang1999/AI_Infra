## 反馈入口与耗时采集

用户通常通过训练方反馈接到问题，step time 变化是最直接的指标；还会观察耗时是否均匀、存储带宽等。希望后续支持自动检测，但阈值、采样与触发动作尚未确定。

| 指标 | 起止位置 | 当前口径 |
| --- | --- | --- |
| step_time | 每个 micro-batch 取数前，到该 micro-batch 训练逻辑返回 | 墙钟耗时；有参数更新时包含更新，其他步骤不等待后续更新 |
| data_get_time | 请求已完成 collate 的 batch，到取得该 batch | 消费侧取数耗时，每个 rank 独立采集，具体接入位置随训练代码调整 |

step_time 不是严格的 GPU 参数更新完成耗时。GPU 异步执行，因此不能直接将 step_time 减去 data_get_time 当成 GPU 计算时间。梯度累积按每个 micro-batch 记录，更新与非更新 micro-batch 分组比较；具体代码接入和上报实现后续补充。

data_get_time 的核心边界是从预先 collate 好的 batch 队列取数，不机械绑定某个 next()。测量可能包含队列没有可用数据时的等待；如果框架封装了搬运或其他处理，应说明实际范围。指标尚待新增，不表述为已上线能力。

启动 warmup 与稳定阶段分别观察，预取准备不混入常规效率统计。

## 数据供给的判断与诊断入口

用户期望数据生产有足够余量，下一 step 能及时取得 batch。data_get_time 较长是消费端等待的调查入口；是否造成 GPU 空闲、延后后续计算或其他 rank 等待，还需联合 step time 和 Profile 判断，不能把所有 CPU 等待时间直接算为 GPU 浪费。

| 耗时分布 | 优先排查方向 | 判断边界 |
| --- | --- | --- |
| 不固定 rank／step，随机且反复出现长等待 | 整体代码链路、存储或 CPU 资源 | 通过发生时间、跨 rank 分布和资源证据查证 |
| 大部分正常，固定一个 rank／节点持续慢 | 局部节点资源、worker 及数据访问路径 | 区分机器问题与该 rank 分配到的数据问题 |
| 长期稳定，偶发孤立慢 step | 异常样本或特殊处理路径 | 记录输入并复现，同时排除瞬时资源波动 |

前两类随机与孤立慢 step 的频率边界已由用户确认。均为优先方向，而非单凭分布即可确认根因。

扩展 rank 后，长尾或共享资源竞争可能放大，并影响线性度；是否随规模持续退化，需要扩展测试确认。

## CPU 侧详细学习笔记

用户实际说明：每个 rank 的 num_workers 通常为 8 或更高，由业务自行配置；容器有明确 CPU 限制，随机型变化，不写统一核数。数据处理中涉及 NumPy、OpenCV，以及 Parquet 读取库的多线程。

除用户已提及的 CPU 计算与 worker 竞争外，下列案例为教学补充，不标为用户亲历案例。核心是区分 CPU 正在工作和 CPU 等待其他环节。

### 多进程与库线程池竞争

并发层次为节点上的多个 rank、每个 rank 的 DataLoader worker、worker 内读取或计算库线程池。需要对照容器 CPU 额度和绑核范围，而非服务器总核数。线程总数多不等于竞争，应确认活跃线程、可运行需求与实际效率。

典型表现：CPU 忙但吞吐低，取数长尾、step 不均匀，增加 worker 后不快反慢；单进程处理快，多 rank 并发处理慢。

通用路径：确认可用资源 → 梳理进程与线程层次 → 区分计算、调度与 I/O 等待 → 调整并发对照 → 验证训练收益。

实验每次改变一个因素：先保持 worker 配置不变调整库线程数，再固定线程设置调整 worker。比较 data_get_time 分布、step time 和端到端吞吐，不只看 CPU 利用率，也不统一推荐所有线程设为 1。

Parquet 是格式，线程行为取决于读取库。按通用方法组织，不假设具体引擎；区分读取库 CPU 与 I/O 线程池，并检查实际存储等待、解码及线程竞争。具体 API 参数留待工具或案例需要时补充。

### 主线程串行工作过重

数据队列可能充足、data_get_time 很短，但主线程整理或计算耗时长，后续 GPU 提交被延后。

| 教学案例 | 表现 | 排查与处理 |
| --- | --- | --- |
| 逐样本 Python 循环 | 单核忙而整机平均利用率不高 | 定位循环热点，尝试批量处理或缓存不变结果 |
| NumPy 计算 | 取数快，输入处理或矩阵计算慢 | 单独测量、相同输入复现，选择等价实现 |
| 反复转换与复制 | 类型转换、小对象构建和重复复制 | 检查次数与数据量，减少重复工作 |
| 指标与日志处理 | 特定步骤变慢、GPU 执行间有空隙 | 降低非必要操作频率做对照，确认端到端影响 |

标记取数、输入整理、forward、backward、更新、指标和日志；用联合 CPU／GPU 时间线判断长 CPU 段是否影响后续执行，再覆盖正确性验证。函数耗时长可能是等待，不直接等于计算量大。

### CPU–GPU 同步等待

教学案例：每步将 GPU loss 通过 item() 取为 CPU 标量并输出。CPU 需要结果可用，调用耗时可能包含等待此前 GPU 工作；不等于取一个数字本身有大量 CPU 计算，也不能把等待重复加到 GPU 耗时上。

常见入口：CUDA Tensor.item()、打印 CUDA Tensor、取回 CPU 结果、依赖 GPU 结果的 Python 分支及显式同步。

| 时间线 | 解读 |
| --- | --- |
| CPU 等待期间 GPU 持续有效执行 | 等待本身未必浪费 GPU 算力 |
| 同步后 CPU 才提交后续工作，GPU 出现空隙 | 可能暴露 CPU 开销、破坏重叠并影响吞吐 |

排查顺序：找同步位置及频率 → 看联合时间线 → 判断结果是否此刻必须使用 → 降低非必要操作或合并取值做对照。验证使用稳定窗口吞吐及正确性。

不能删除必要同步；detach() 不会将 GPU 数据变成 CPU 数据，后续 item() 仍可能等待；将同步后移可能只是转移等待位置。常驻墙钟 step_time 可能在某步承担此前异步工作的等待，不能仅凭单步时长归因。

### 已列出的其他类型，后续展开

| 类型 | 教学情景与调查入口 |
| --- | --- |
| CPU 配额或同机竞争 | 宿主机空闲但容器受限，或其他任务加入后变慢；查额度、绑核及限流 |
| 转换、复制与进程间传递 | 读取快但大量小对象、collate 或传递慢；拆分阶段并查数据量 |
| 日志、文件与锁等待 | 某个 rank 或周期性步骤慢；区分处理、实际写入和锁等待 |

这些类型目前只有入口，不补造完整实战结论。

## GPU 指标与 Profile 判读

用户的实际顺序是先看 GPU 指标，再采集 Profile。以相同硬件 baseline 排查明显异常；利用率、功率和显存为主要观察项，SM 活跃率辅助判断，怀疑设备问题时再查频率与温度。比较变慢前后的曲线及跨 GPU 差异。

实际遇到过某个 rank 对应 GPU 温度异常：交给 IT 团队隔离检测，当前训练任务更换节点后恢复正常。没有确认频率或热降频证据，不写成已证实热降频，也不补造硬件根因。

Profile 先寻找单次耗时明显异常的 CPU 操作、GPU kernel 或通信事件，结合 baseline 判断；不采用固定 100 ms 阈值，不以累计耗时替代这里的单次判断。通信耗时长时比较相关 rank，优先关注 data_get_time 较长者，对齐对应 step 与通信组。

HTA 可以辅助聚合各 rank 的计算、通信、内存事件、空闲与长 kernel 分布，再回到原始时间线核实。大模型可辅助整理具体异常、候选原因及下一步验证，结论需由运行证据与对照支持。计算与通信可能重叠，分类时长不能机械相加成 step 耗时。

## GPU 计算间隙的定义与排查

### 定义与边界

“计算间隙”是前一段计算 kernel 结束、后一段尚未开始之间的时间，不能直接等同于整张 GPU 空闲。

| 观察范围 | 解读 |
| --- | --- |
| 某条 stream 空白 | 其他 stream 可能仍执行 |
| 无计算 kernel，但有 memcpy／NCCL | 计算暂停，设备仍可能搬运或通信 |
| 已采集的各 stream 均无相关活动 | 是该任务的 GPU 空闲线索；仍需确认采集完整性和其他进程活动 |

关注稳定阶段相对 baseline 新增的间隙、频率及对 step 推进的影响。启动、结束和采集开销造成的空白应区分；不设统一时长阈值，大量短间隙也可能累积影响吞吐。

### 核心判断：未及时提交，还是已提交但不能执行

找到间隙后的第一个 kernel，向前关联其 CPU／CUDA 调用及执行依赖。

| 证据 | 优先方向 |
| --- | --- |
| 对应 CUDA 调用很晚才发生 | CPU 在取数、计算、调度或等待，未及时提交 |
| 已提交但 kernel 迟迟不开始 | 查前序工作、stream／event 依赖、传输及资源等待 |

CPU 提交和 GPU 实际执行时间不同。CPU 同步等待时 GPU 可能仍有效工作，还要检查同步结束后是否产生新的空隙，不能把等待全算成浪费。

### 专业排查路径

1. **确认异常**：选择 warmup 后的稳定窗口，对比同硬件 baseline，确定间隙的位置、次数与影响。
2. **展开完整时间线**：同时看 CPU 主线程、阶段标记、CUDA API、GPU 各 stream 的 kernel／memcpy／NCCL，以及对应 data_get_time。
3. **追查下一个 kernel**：关联提交时间和依赖，区分工作未及时提交与执行条件未满足。
4. **进入原因分支**：按下表定位，不凭单个空白区域归因。
5. **跨 rank 验证顺序**：确认哪个 rank 最先延后及其他 rank 随后的等待，而非把等待最长者直接当根因。
6. **对照验证**：一次调整一个因素，确认间隙缩短、稳定窗口吞吐改善及结果正确。

| 分支 | 时间线线索 | 下一步 |
| --- | --- | --- |
| 数据供给 | 取数等待增长，取得 batch 后才继续提交 | 查 worker、collate、存储与数据处理 |
| CPU 提交 | batch 已取得，主线程仍计算或未获得调度 | 查热点、线程竞争和配额，必要时用 perf |
| 同步等待 | 主线程获取 GPU 结果或同步后才继续提交 | 检查同步必要性及后续重叠 |
| 搬运或依赖 | 后续计算依赖传输或 event 完成 | 查耗时与依赖，判断能否合理重叠 |
| 分布式不均衡 | 某个 rank 先延后，其他 rank 随后等待 | 对比对应 step、通信组及各 rank 路径 |

典型证据链：rank A 取数延迟 → A 计算／通信提交延后 → 其他 rank 对应通信等待增加 → 整步耗时增加。该链用于解释方法，未附实际 trace，不作为新的实战案例。

工具分工：PyTorch Profiler 作初步阶段与活动关联，Nsight Systems 深入 CPU 调度、阻塞状态与 CUDA 调用关系，HTA 辅助跨 rank 筛选。具体采集命令留待 Profile 专项。

快速总结：**找异常间隙 → 确认仍在执行的活动 → 追查下一 kernel 的提交与依赖 → 定位原因 → 对照验证。**
