# 训练慢与变慢排查详细解释

[快速排查 SOP](训练慢与变慢排查SOP.md)

本教程从指标初筛进入时间线诊断，解释数据、CPU、GPU 与通信问题的判断依据及验证方法。

## 一、确认问题与比较基准

区分持续慢、运行中变慢与耗时波动。先对照相同硬件 baseline，观察稳定阶段 step time、端到端吞吐及各 rank 耗时分布，不用单次 GPU 利用率确定瓶颈。

| 比较项 | 需要记录的条件 |
| --- | --- |
| 模型与数据 | 代码版本、模型路径、数据版本、输入 shape／长度和异常样本 |
| 训练配置 | 每卡 batch、精度、梯度累积、并行策略、GPU 数及检查点恢复状态 |
| 运行环境 | 相同硬件、容器 CPU 资源、软件与驱动版本、存储路径和同机负载 |
| 时间窗口 | warmup／稳定阶段、是否包含评估或 Checkpoint、采集是否开启 |

条件不同不意味着无法分析，但要先解释差异，避免把更多工作量写成执行退化。无历史 baseline 时，可用同条件正常运行或健康节点建立对照，并说明限制。

## 二、采集 step_time 与 data_get_time

### 按 micro-batch 计量

每个 micro-batch 都涉及取数，因此在梯度累积场景按 micro-batch 记录 step_time。它从取数据之前开始，到该 micro-batch 训练逻辑返回结束；执行 optimizer 更新时包含该更新调用，未执行更新时不把后续 micro-batch 的耗时算进来。

这是 CPU 侧墙钟观测，不是 GPU 更新完成的精确计时。分别比较更新与非更新 micro-batch，不能把正常的更新步骤额外开销直接判为随机变慢。

### data_get_time 测的是消费端

目标边界：请求已经完成 collate 的 batch，到消费端获得 batch。按实际训练代码接入该测量，并逐 rank 独立记录。

具体位置不机械等同于 next(loader)：若封装还包含搬运、转换或其他处理，应找对边界，或明确指标实际包含什么。取数时间也可能包含数据传递开销，不等同于 worker 生产总耗时。

下面只示意边界；train_micro_batch 是使用者已有训练逻辑的占位名称，需要自行接入，不是完整训练程序：

```python
from time import perf_counter

# batch_iter 必须对应符合目标边界的数据获取接口。
t0 = perf_counter()
batch = next(batch_iter)
t1 = perf_counter()

train_micro_batch(batch)  # 按已有梯度累积逻辑执行，不强制每次更新。
t2 = perf_counter()

data_get_time = t1 - t0  # 秒
step_time = t2 - t0      # 秒；CPU 侧墙钟口径，不额外同步 GPU。
# 将 rank、micro_step、是否参数更新、阶段和两个耗时低开销记录。
```

每 rank 独立采集，保留 micro-step／必要的样本标识、更新标记和阶段，以便对照；避免为记录指标逐步回传 GPU 标量或同步写大量日志。worker 多进程、框架预取与数据搬运的实现应单独核对。[PyTorch DataLoader](https://docs.pytorch.org/docs/2.14/data.html)

warmup 与稳定阶段分别统计。不设通用耗时阈值；优先看持续等待、长尾、rank 差异及其与 step 的关联。异步 GPU 工作可能在某次同步处集中等待，step_time - data_get_time 不等于 GPU 计算时间。[PyTorch CUDA 语义](https://docs.pytorch.org/docs/2.14/notes/cuda.html)

## 三、数据链路是否及时供给

生产端应有足够余量，尽量提前准备下一 batch。data_get_time 长表示消费端等待或获取开销增加；结合时间线判断是否延后 GPU 计算提交，以及其他 rank 是否在后续通信等待。

| 分布 | 优先检查 | 验证方式 |
| --- | --- | --- |
| 随机位置、反复长等待 | 代码处理链路、共享存储、CPU 与并发配置 | 关联发生窗口及资源，分段计时与单变量对照 |
| 固定 rank／节点慢 | 本地资源、worker、数据分配和访问路径 | 比较正常节点，必要时换节点或对照相同输入 |
| 稳定运行中孤立慢 step | 异常输入与特殊处理路径，或瞬时资源波动 | 记录样本与运行窗口，离线复现后确认 |

向生产端追查读取、解码／预处理、getitem、collate、传递等阶段，不默认“取数慢就是存储慢”。数据获取正常也不排除取数之后的 CPU 工作拖慢训练。

## 四、CPU 侧诊断入口

| 方向 | 观察线索 | 下一步 |
| --- | --- | --- |
| 资源与线程竞争 | CPU 忙但数据吞吐低，增加 worker 后更慢 | 对照容器资源，梳理 rank、worker 与库线程池；分别调整并发 |
| 串行工作 | 取数快，主线程处理长，GPU 后续提交延迟 | 标记 Python 循环、NumPy 计算、转换复制、指标与日志 |
| 同步等待 | CPU 调用长，但期间 GPU 仍执行 | 找取值、回传与同步，检查是否破坏后续重叠 |
| 配额、I/O 与锁 | 整机平均负载不能解释局部慢 | 查容器额度、线程状态、阻塞与相关日志 |

worker 数与库线程设置应结合容器实际 CPU 额度确定，不能只依据服务器总核数。Parquet 的并发由具体读取实现决定，与 NumPy／OpenCV 等线程池一起梳理。

CPU 利用率高不等于效率高，线程多也不直接证明竞争。一次调整一个变量，以数据等待、step 和吞吐验证。必要时用 CPU 采样和调度记录确认热点与等待。[PyTorch 多进程说明](https://docs.pytorch.org/docs/2.14/notes/multiprocessing.html)

## 五、GPU 指标与 Profile 初筛

先指标、后 Profile：对比利用率、功率和显存，辅助看 SM 活跃率；怀疑设备问题时检查温度、频率及降频原因。GPU／SM 活跃不直接等于有效训练计算，见[GPU Hang 专题](../训练报错排查/训练卡住排查：通信等待型GPU_Hang.md)。

实际案例：某个 rank 的 GPU 温度异常，IT 团队隔离检测，当前任务换节点后正常。换节点恢复说明问题与原节点或相关环境有关，但不能单独确认热降频。进一步可关联频率、thermal slowdown／功率限制与操作耗时，解释设备状态。[NVIDIA 指标与降频说明](https://docs.nvidia.com/deploy/nvidia-smi/index.html)

Profile 优先看单次耗时明显异常的 CPU 操作、GPU kernel、memcpy 和通信事件，再结合正常值与重复次数判断。异常判断以可比较的正常耗时和输入条件为依据；高累计耗时可以选热点，但不能替代单次异常判断。

### 持续执行但变慢：诊断分支

按以下方向区分工作量变化、执行路径变化与性能退化。

| 观察结果 | 候选原因与确认方法 | 处理方向 |
| --- | --- | --- |
| 操作次数变多 | 输入路径、模型逻辑、重复计算或梯度累积条件变化；对齐比较区间 | 修复意外重复或确认新增工作是否必要 |
| 同类操作单次变长，输入变大 | shape、长度、batch 内组成或 padding 变化 | 先确认实际工作量；优化异常输入处理，不称为相同工作量退化 |
| 精度或 kernel 路径变化 | 检查 dtype、混合精度、软件版本及 kernel 选择 | 单因素对照配置，验证性能与数值正确性，不默认降低精度 |
| 编译或算法选择频繁出现 | 检查是否只在首次运行，或新 shape 反复触发 | 区分 warmup 与持续发生，调整配置前确认适用条件 |
| 显存曲线与分配／复制活动变化 | 检查 input 波动、分配和搬运，不凭“占用高”归因 | 先减少已证实的重复工作，必要时进入显存诊断 |
| 固定 GPU 的相同 kernel 变慢 | 比较设备状态与相关环境，排除工作量差异 | 隔离异常资源或交硬件团队检测，再用同负载验证 |
| 变长的是 NCCL 操作 | 对应通信组内比较输入、调用、各 rank 就绪时间及链路 | 区分对端掉队、通信配置与网络异常，不能直接认定网络慢 |

同名 kernel 不保证工作量或执行环境相同。分开看 CPU API、排队和实际 kernel 执行时长；已提交后的排队可能是前序工作正常占用，不能将所有排队都视为异常。动态输入、分配、算法选择和精度调整需按实际配置验证。[PyTorch 性能指南](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html)、[Nsight Systems 分析指南](https://docs.nvidia.com/nsight-systems/AnalysisGuide/index.html)

## 六、GPU 计算间隙排查

间隙是前一段计算 kernel 结束到后一段开始之间的时间。某条 stream 空白不代表 GPU 空闲；无计算 kernel 时也可能有 memcpy／NCCL。查看已采集的所有相关 stream，并确认采集完整性、其他进程及采集开销。

核心问题：**下一 kernel 是未及时提交，还是已提交但执行依赖未满足？**

| 时间线证据 | 下一步 |
| --- | --- |
| CPU／CUDA 调用本身发生得晚 | 追查取数、CPU 处理、调度和同步等待 |
| 调用已发生，GPU 执行较晚 | 追查前序工作、stream／event 依赖、传输与资源 |

找新增间隙及其对 step 的影响 → 展开 CPU／CUDA／GPU 联合时间线 → 关联间隙后的第一个 kernel → 沿提交或依赖分支调查 → 跨 rank 确认因果顺序 → 对照验证。

典型教学链路：某 rank 取数延后，计算／通信提交随后延后，其他 rank 等待增加。若 CPU 在同步时 GPU 仍忙，等待本身未必浪费算力；还需看同步结束后的空隙。避免给正常异步提交每步添加同步来“方便分析”，改变原执行行为。

## 七、通信、聚合与分布式入口

通信长时，优先比较对应 step、通信组和疑似 data_get_time 较长的 rank。寻找最先延后的环节，不以等待最长者自动认定根因；缺少业务指标时按代码接入阶段记录。

HTA 可辅助聚合计算、通信、内存活动、空闲和 kernel 分布，再回到原始 trace 确认。大模型用于整理异常、证据、候选原因和下一步验证，不能替代运行证据。重叠的活动耗时不能机械相加。[HTA 官方说明](https://github.com/facebookresearch/HolisticTraceAnalysis)

固定每卡 batch 增加 GPU 时，全局 batch 随规模增长；检查每卡工作量与配置是否一致，再比较吞吐变化。先调查数据长尾、共享资源竞争、rank 不均衡及通信开销。以扩展前后的测试结果确认问题，不据卡数增加直接断言根因。

工具主线为 PyTorch Profiler，nsys 补系统和 CUDA 时间线，perf 深入 CPU 热点及调度。采集开销会影响性能，shape／stack 等选项按需要启用。[PyTorch Profiler](https://docs.pytorch.org/docs/2.14/profiler.html)

## 八、验证与证据记录

同硬件、同工作负载和配置，在 warmup 后的代表性稳定窗口验证；区分更新与非更新 micro-batch，记录吞吐、step 分布、data_get_time 长尾及 rank 差异。覆盖原来的触发条件和数据范围，一次改一个因素。

正式验收用无重型采集干扰的端到端运行；必要的严格基准计时可在测量窗口边界处理 GPU 完成条件，与常驻墙钟指标区分，不逐步强制同步。

记录改动前后配置、异常输入／阶段、关键证据、对照效果与正确性结果。指标改善但端到端吞吐未改善，继续确认是否改到了关键路径，不把局部收益等同于整体收益。

持续监控可关注 step 耗时退化、波动和取数长尾；告警阈值应依据任务 baseline、持续条件及正常阶段制定。
