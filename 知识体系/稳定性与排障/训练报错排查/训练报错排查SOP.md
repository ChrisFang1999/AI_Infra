# 训练报错排查 SOP

用于多机多卡训练报错，以及任务未退出但停止推进时的初步定位。

[通信等待型 GPU Hang 专题](训练卡住排查：通信等待型GPU_Hang.md) · [查看详细解释](训练报错排查详细解释.md) · [返回知识库](../../../README.md)

## 排障流程图

按顺序查找线索；发现异常后进入对应诊断。

```mermaid
flowchart TD
    A{"① 多机日志<br/>有明确异常？"}
    A -- 有 --> B["定位代码、I/O<br/>或通信不匹配问题"]
    A -- 无 --> C{"② 平台与硬件监控<br/>有相关异常？"}
    C -- 有 --> D["检查对应节点<br/>及故障资源"]
    C -- 无 --> E{"③ 是否有通信等待型<br/>GPU Hang 迹象？"}
    E -- 有 --> F["查堆栈分组与连续快照<br/>定位偏离 rank"]
    E -- 无或不确定 --> G["查连续堆栈与日志<br/>定位其他阻塞路径"]
```

- **通信不匹配**：对应通信的 size 不一致，或部分 rank 跳过通信、调用顺序错位。检查相关代码，尤其是手动编写的通信调用。
- **GPU Hang 迹象**：任务不推进，多数 GPU 持续 100% 利用率且低功率；自动检测规则见[详细解释](训练报错排查详细解释.md)。全 0% 另归其他阻塞；不满足该模式也继续查堆栈。
- 日志向 timeout 之前追查，同时保留 watchdog 的通信信息。仍无明确线索时，补充证据或安排复现。具体检查项见下表。

## 快速排查

先确认异常时间、节点及 rank 对应关系，区分仍存活的现场和退出前留存的记录。按下表寻找线索；已有明确证据时，直接沿对应方向调查，不必机械查完所有项目。

| 步骤 | 检查什么 | 关注什么、下一步怎么走 |
| --- | --- | --- |
| 1. 多机日志 | 各节点、各 rank 的训练日志，尤其是末尾报错之前的内容 | 优先找明确代码异常、I/O 异常及调用位置。watchdog timeout、SIGTERM 通常是连带表现，沿时间线向前追查；不要仅凭最后一条报错认定根因；仍需比较 watchdog 日志中的通信操作与数据量。 |
| 2. GPU 状态 | GPU 利用率、功率及训练是否推进 | 多数 GPU 持续 **100%** 利用率、低功率，少数为 0% 时，优先查偏离 rank 的节点日志。该模式是当前环境的通信等待型 GPU Hang 线索，需与堆栈交叉判断。 |
| 3. 平台事件 | 平台日志、K8s 作业及节点事件、存储异常 | 查找与故障时间关联的调度、终止、节点或存储事件，判断其是否能解释训练异常。 |
| 4. 硬件监控 | 显存和内存、IB 网卡、网络及存储流量 | 查 OOM 证据、网卡错误、丢包及存储流量异常；关联时间和节点，避免只凭占用率或单条曲线认定原因。 |
| 5. 堆栈分析 | 跨 rank 分组及连续堆栈快照 | 先找偏离多数执行路径的 rank，再看是否长期停留同一位置，同步查相关代码报错、系统日志与监控。即使前面没有明显异常，也进入此步。 |

现场仍存活时及时保留诊断证据，不必等待自动 GPU Hang 判定。全 0% 且训练不推进属于另一类阻塞，不能因未满足 GPU Hang 条件就认定训练正常。

## 堆栈判断入口

**分组找偏离 → 连续快照看停留 → 日志交叉验证。**

典型线索：多数 GPU 处于通信等待，少数 rank 的连续 CPU 堆栈停留于数据 wait 或 NumPy 计算。CPU 堆栈不必显示在 allreduce 调用处，应结合日志和通信信息判断。重点调查后者，将其作为解释通信等待的阻塞来源，再追查该位置为何不能推进。

工具从训练启动起每分钟采集堆栈，发生训练卡住时输出最近 10 次快照；无响应 rank 的最后成功记录只能说明最后可观测位置。

## 排查结果记录

记录异常时间与范围、候选 rank/节点、关键日志或堆栈证据，以及当前定位到的阻塞位置。区分“已找到阻塞点”和“已解释其发生原因”。

如果现有证据仍不足，保留未解决问题，不把候选原因写成确定根因。数据等待、CPU 计算及存储流量异常可继续参考[训练慢排查 SOP](../训练慢与变慢排查/训练慢与变慢排查SOP.md)；检测规则与判断边界见[详细解释](训练报错排查详细解释.md)。
